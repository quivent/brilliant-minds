# Brian Kernighan: Philosophy and Approach

## Quotes, Methods, and Intellectual Character

---

## I. On Clarity and Simplicity

**"Write clearly — don't be too clever."**

**"Say what you mean, simply and directly."**

**"Debugging is twice as hard as writing the code in the first place. Therefore, if you write the code as cleverly as possible, you are, by definition, not smart enough to debug it."**

**"Controlling complexity is the essence of computer programming."**

**"Clarity is often achieved through brevity."**

**"Write clearly — don't sacrifice clarity for efficiency."**

**"Mechanical rules are never a substitute for clarity of thought."**

---

## II. On Style and Practice

**"Don't comment bad code — rewrite it."**

**"Don't just echo the code with comments — make every comment count."**

**"Make sure comments and code agree."**

**"Use library functions whenever feasible."**

**"Make the coupling between modules visible."**

**"Let the data structure the program."**

**"Choose a data representation that makes the program simple."**

**"Each module should do one thing well."**

**"Replace repetitive expressions by calls to common functions."**

**"Use the good features of a language; avoid the bad ones."**

**"Capture regularity in control flow, irregularity in data."**

---

## III. On Testing and Debugging

**"The most effective debugging tool is still careful thought, coupled with judiciously placed print statements."**

**"It is a fundamental principle of testing that you must know in advance the answer each test case is supposed to produce. If you don't, you are not testing; you are experimenting."**

**"The single most important rule of testing is to do it."**

**"Each new user of a new system uncovers a new class of bugs."**

**"Believe the terrain, not the map."**

**"Another effective debugging technique is to explain your code to someone else. This will often cause you to explain the bug to yourself. One university computer center kept a teddy bear near the help desk."**

---

## IV. On Systems and Composition

**"Even though the UNIX system introduces a number of innovative programs and techniques, no single program or idea makes it work well. Instead, what makes it effective is the approach to programming, a philosophy of using the computer. Although that philosophy can't be written down in a single sentence, at its heart is the idea that the power of a system comes more from the relationships among programs than from the programs themselves."**

**"90% of the functionality delivered now is better than 100% delivered never."**

---

## V. On Languages

**"C retains the basic philosophy that programmers know what they are doing; it only requires that they state their intentions explicitly."**

**"C is a razor-sharp tool, with which one can create an elegant and efficient program or a bloody mess."**

**"The languages that succeed are very pragmatic, and are very often fairly dirty because they try to solve real problems."**

**"Every language teaches you something, so learning a language is never wasted, especially if it's different in more than just syntactic trivia."**

On C++: Uses only 10% of features; with C, uses 75-90%. "Too big a language."

---

## VI. On Motivation and Work

**"Do what you think is interesting, do something that you think is fun and worthwhile, because otherwise you won't do it well anyway."**

**"Leap in and try things. If you succeed, you can have enormous influence. If you fail, you have still learned something, and your next attempt is sure to be better for it."**

**"The way to learn to program is to write code and rewrite it and see it used and rewrite again. Reading other people's code is invaluable as well."**

**"I think everything I've done I've done with somebody else: it's more fun to work with other people than to lock yourself in an office and do it all by yourself. And I think I'm probably better at listening and finding somebody who's got a good idea and then working with that person on the good idea."**

**"Learn how to do it yourself. Use the mechanical aids, but learn what you're doing."**

---

## VII. On the World

**"There are only two real problems in computing: computers are too hard to use and too hard to program. We've made enormous progress on both of these over the past fifty years, but they are still the real problems."**

**"As we understand better how to do the small things we take on bigger and more complicated things and so in a sense we're always up to our armpits in alligators."**

---

## VIII. The Four Principles (from The Practice of Programming)

1. **Simplicity** — keep programs short and manageable
2. **Clarity** — make them easy to understand for people as well as machines
3. **Generality** — they should work in a broad range of situations and adapt to new ones
4. **Automation** — let the machine do the work

---

## IX. The Elements of Style (Selected Maxims)

From the 62 rules in *The Elements of Programming Style*:

1. Write clearly — don't be too clever
2. Say what you mean, simply and directly
3. Don't comment bad code — rewrite it
4. Don't just echo the code with comments — make every comment count
5. Use library functions whenever feasible
6. Let the machine do the dirty work
7. Replace repetitive expressions by calls to common functions
8. Choose variable names that won't be confused
9. Make the coupling between modules visible
10. Each module should do one thing well
11. Use the good features of a language; avoid the bad ones
12. Capture regularity in control flow, irregularity in data
13. Follow each decision as closely as possible with its associated action
14. Use the 'telephone test' for readability
15. Trying to outsmart a compiler defeats much of the purpose of using one
